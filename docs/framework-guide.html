Guide de développement

Ce document explique comment démarrer l’environnement Le Monde de Lila, créer de nouveaux modules, étendre les menus Swing et tirer parti de l’infrastructure existante.

1. Lancer l’outillage

  1. Depuis la racine du projet, exécuter powershell -ExecutionPolicy Bypass -File .\start-lila.ps1. Le script installe Maven (si nécessaire), démarre les serveurs Symfony (HTTP + WebSocket) et construit le client Java.
  2. Les logs des processus backend se trouvent dans logs\backend-*.log.
  3. Si vous ne souhaitez compiler que le client, exécutez : 
    cd .\java-client
..\tools\apache-maven-3.9.6\bin\mvn.cmd -pl client-app -am package -DskipTests

2. Comprendre l’architecture

  • Modules : toutes les briques partagent l’interface LilaModule. La classe com.lemondelila.framework.core.module.FrameworkBootstrap charge automatiquement les implémentations via ServiceLoader, puis appelle configure() et start().
  • Injection de dépendances : le conteneur ApplicationContext (framework-core) fournit les services. Chaque module enregistre ses bind via le builder.
  • Client Swing : le point d’entrée com.lemondelila.client.AppLauncher crée la fenêtre LilaFrame et affiche l’écran HomeScreen, qui pilote des panneaux spécialisés (LandingPanel, LoginFormPanel, RegisterFormPanel).
  • Backend Symfony : exposé sous http://127.0.0.1:8000/api (par défaut). Le contrôleur App\Module\User\Controller\AuthController gère les routes /api/login et /api/register.

3. Créer un module applicatif

  1. Ajoutez un nouveau package (ex. com.lemondelila.client.module.catalog) dans java-client.
  2. Implémentez LilaModule : 
    public final class CatalogModule implements LilaModule {
    @Override
    public void configure(ApplicationContext.Builder builder) {
        builder.bind(CatalogService.class, CatalogService::new);
    }

    @Override
    public void start(ApplicationContext ctx) {
        ctx.get(CatalogService.class).warmup();
    }

    @Override
    public int order() {
        return 10; // plus grand => démarré après les frameworks
    }
}
  3. Déclarez le module dans java-client/client-app/src/main/resources/META-INF/services/com.lemondelila.framework.core.module.LilaModule pour que ServiceLoader l’instancie.
  4. Si le module doit afficher un écran, utilisez ScreenManager : 
    ScreenManager manager = context.get(ScreenManager.class);
manager.register(context.get(MyScreen.class));
manager.show("my-screen-id");
Astuce : Décomposez la vue en sous-composants (comme HomeScreen et ses panels) pour faciliter la maintenance et le test unitaire.

4. Ajouter un menu ou une vue Swing

  1. Les menus se créent via com.lemondelila.framework.ui.menu.MenuFactory. Exemple : 
    MenuFactory menuFactory = context.get(MenuFactory.class);
menuFactory.create("Jeu", builder -> builder
    .item("Nouveau niveau", () -> eventBus.publish(new NewLevelRequested()))
    .item("Quitter", () -> System.exit(0))
);
  2. Pour un nouvel écran, créez une classe implémentant Screen (voir HomeScreen) et enregistrez-la auprès du ScreenManager.
  3. Ajoutez vos actions au ActionManager pour bénéficier des raccourcis, puis attachez la vue via actionManager.attachTo(component);.

5. Déclarer des raccourcis clavier

Les raccourcis sont centralisés dans ActionManager (framework-ui). Exemple simplifié :

AbstractAction toggleCatalog = new AbstractAction("catalog:toggle") {
    @Override public void actionPerformed(ActionEvent e) {
        screenManager.show("catalog");
    }
};
actionManager.register("catalog.toggle", () -> toggleCatalog, KeyStroke.getKeyStroke("alt G"));
shortcutRegistry.register(KeyStroke.getKeyStroke("alt G"), "Ouvrir le catalogue");
N’associez pas ENTER à des actions globales depuis l’accueil : laissez les panneaux gérer la touche via JComponent.WHEN_FOCUSED comme pour LoginFormPanel et RegisterFormPanel.

6. Consommer les API backend

  1. Utilisez RestClient (framework-network) fourni par NetworkModule.
  2. Le module réseau lit les propriétés network.http.base et network.ws.url depuis config/client.properties (copie incluse dans client-app/src/main/resources).
  3. Un contrôleur type (voir AuthController) : 
    JsonNode response = restClient.post("login", Map.of(
    "username", request.username(),
    "password", String.valueOf(request.password())
));
  4. Complétez l’API Symfony si nécessaire (ex. App\Module\User\Controller\AuthController pour l’inscription).

7. Checklist de validation

  • Tests locaux : mvn -pl client-app -am package -DskipTests.
  • Lint/format : la base est compatible avec spotless/IDEA – pas encore automatisé.
  • Accessibilité : fournissez une description courte aux boutons (cf. LandingPanel) et enregistrez tout raccourci dans AccessibleShortcutRegistry.
  • Journalisation : utilisez org.slf4j.Logger (implémentation slf4j-simple incluse).
  • Shutdown propre : si votre module ouvre des ressources (threads, WebSocket), implémentez stop() et fermez-les comme dans AccessibilityModule.

8. Options locales et préférences

Le client stocke les préférences utilisateur dans config/settings.json via AppSettingsService. Les options disponibles couvrent :

  • Volume des effets du jeu.
  • Volume de la musique.
  • Affichage ou non d’une confirmation lorsque l’on ferme l’application.
  • Activation/désactivation du tchat global et demande de confirmation avant de fermer la fenêtre de tchat.

Ces paramètres sont éditables depuis le menu principal (Entrée → Options). La touche Alt+R permet de revenir au menu d’accueil, tandis que Alt+C et Alt+I contrôlent respectivement la connexion et l’inscription.

9. Tchat en temps réel

Une fois connecté, le menu principal propose l’option Tchat. Cette vue ouvre une fenêtre Swing non modale qui se connecte au WebSocket network.ws.url avec le token JWT renvoyé par le login.

  • Connexion via ChatConnectionFactory, qui ajoute automatiquement ?token=<jwt> à l’URL.
  • Les messages entrants sont normalisés (auteur, texte, horodatage) et affichés en lecture seule.
  • L’envoi publie {"type":"chat-send","text":"..."} : côté Symfony, PresenceRealtimeBroker diffuse ensuite chat-message à tous les clients.
  • En cas d’erreur réseau, le DialogService affiche un message tout en conservant la fenêtre ouverte.

10. Module Nemesis

Le mini-jeu Mission Nemesis a ete rationalise : les classes Java utilisent des noms concis Nemesis* et sont regroupees sous com.lemondelila.client.gamelogic.missionnemesis.

  • Controle : NemesisController pilote les flux asynchrones et notifie les vues.
  • Acces reseau : NemesisRemoteClient centralise les appels REST (creation de partie, rafraichissement, tirs).
  • Modele : NemesisSession, NemesisState et NemesisStateMapper exposent l'etat du jeu cote client.
  • Interface : NemesisScreen assemble plusieurs panneaux dediques (NemesisControlsPanel, NemesisGridPanel, NemesisLogPanel, NemesisFooterPanel).

Les anciennes classes prefixees MissionNemesis* ont ete supprimees. Pensez a mettre a jour vos imports lors d'un rebase.

11. Configuration reseau

Le client Swing charge les URLs WebSocket depuis client-app/src/main/resources/config/client.properties.

  • network.ws.url=ws://127.0.0.1:8081/ws pour la table de jeu Nemesis.
  • network.ws.presence=ws://127.0.0.1:8081/presence pour le tchat et la presence.

Le script start-lila.ps1 demarre php bin/console app:realtime:serve --env=dev qui ecoute sur 127.0.0.1:8081. Si vous modifiez APP_WS_HOST/APP_WS_PORT cote backend, synchronisez ce fichier pour eviter les erreurs de connexion.
