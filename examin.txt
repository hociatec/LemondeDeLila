
UI & Expérience

Configuration & Données
- Vérifier les écrans restants (catalogue, autres jeux) pour traquer d'éventuelles chaînes encore codées en dur et les migrer vers les `ResourceBundle` afin d'uniformiser l’internationalisation (Accueil, Menu principal et Panier Express sont désormais migrés).
- Certains écrans manipulent encore directement les services métiers dans leur UI ; poursuivre la séparation présentation/service permettra de changer l’UI sans toucher aux contrôleurs.

Accessibilité & Qualité

- La logique d’annonce/accessibilité se répète dans chaque jeu (`PanierExpressRootView.java:300+`, `DameNatureScreen.java:180+`). Extraire des composants `NarrationPanel`, `AccessibleStatus` génériques renforcerait la cohérence et la réutilisabilité.

Travaux restants côté client :
- Injecter les composants (presenters, loaders, contrôleurs) via `ApplicationContext` pour éviter les `new` dans les écrans.
- Extraire les composants UI communs (cartes catalogue, listes, panneaux d’état, raccourcis et narration) vers `framework-ui` pour les partager entre features.
- Créer une API plugin (jeux, écrans catalogue, etc.) avec enregistrement ServiceLoader pour ne plus modifier `ApplicationModule` à chaque ajout.
- Factoriser `RestClient` et `RealtimeGateway` (auth, retries, messages typés) puis mutualiser les `RealtimeChannel`.
- Ajouter une vraie stratégie de tests (unitaires DI/réseau/composants Swing + intégration) pour fiabiliser les briques réutilisables.

Compléments remarqués :
 - Les écrans restants (catalogue avancé, jeux) utilisent encore des chaînes codées en dur ; il faut déplacer toutes les ressources dans `messages.properties`.
 - Plusieurs vues instancient encore elles-mêmes leurs orchestrateurs (home, Panier Express, etc.) : passer par `ApplicationContext` et injecter presenters/controllers assurera meilleure testabilité et réutilisabilité.
 - Le socle accessibilité (StatusBanner, narration, raccourcis globaux) doit être converti en composants réutilisables (`AccessibleStatusPanel`, `NarrationPanel`) afin de réduire les duplications relevées dans les jeux.
 - La couche réseau ne traite pas les préoccupations cross-cutting (auth automatique, retries, instrumentation, sécurisation des tokens) ; une stratégie commune pour `RestClient`, `RealtimeGateway` et les canaux temps réel est nécessaire.
 - Très peu de tests existent (juste `ApplicationContextTest` et `AccessibilityServiceTest`) ; capitaliser sur `ScreenManager`, `ActionManager`, `RestClient` avec des tests unitaires/UI garantira la stabilité des composants réutilisés.

Priorités pour avancer :
1. Créer des SPI + discovery automatique pour écrans/controllers/plugins afin d’éviter les registrations manuelles.
2. Factoriser le kit UI/accessibilité (status, narration, raccourcis) et le mutualiser pour tous les écrans.
3. Renforcer la couche réseau et session (tokens sécurisés, retries, headers auth) via des services partagés.
4. Ajouter une vraie stratégie de tests (unitaires et d’intégration) sur les composants clés.

Synthèse refonte restante
-------------------------
- `ApplicationModule` reste figée avec une liste de modules statiques (`java-client/.../ApplicationModule.java:27-40`) : introduire un SPI (ServiceLoader) pour enregistrer automatiquement les modules/écrans/contrôleurs et éviter les retouches globales à chaque feature.
- Mutaliser le socle UI/accessibilité : extraire StatusBanner, panneaux de narration, listes accessibles et raccourcis globaux dans `framework-ui` pour que les écrans (catalogue, jeux, social) n’empilent plus leur propre logique (`CatalogScreen.java:24-199`, `PanierExpressRootView.java`, `DameNatureScreen.java`).
- Homogénéiser l’injection : certains écrans construisent encore leurs presenters/services via `new` (ex. `HomeScreen`), ce qui va à l’encontre de la DI. Tout doit être résolu par `ApplicationContext` pour gagner en testabilité.
- Couche réseau : `RestClient` et les services métier répliquent la gestion du token et ne gèrent ni retries ni instrumentation (`GameCatalogService.buildAuthHeaders`, `MessagingService.authHeaders`, `TokenAwareRealtimeGateway`). Ajouter une couche commune (interceptors, gestion des `RealtimeChannel`, rotation/refresh JWT) avant d’exposer de nouvelles features temps réel.
- Menu et fonctionnalités sociales : « Rejoindre une table », social et présence restent des placeholders (`MainMenuPresenter` déclenche `featureSoon`). Il faut brancher ces boutons sur les modules backend existants (rooms/presence) pour refléter la refonte.
- Sécurité backend/client : le plan de `afaire.txt` (CSRF, rate limiting, rotation JWT, chiffrement des messages, signature du client Swing) n’est pas encore appliqué ; à traiter avant la stabilisation.
- Qualité : seulement deux tests unitaires existent. Prioriser des tests sur `ScreenManager`, `ActionManager`, les services réseau (HttpClient mocké) et un premier test d’intégration Swing, puis les inclure dans la pipeline Maven (voir `start-lila.ps1`).
