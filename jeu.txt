Gameplay client-wx - implementation clavier generique
=====================================================

But
---
Le client wx doit permettre de jouer a un jeu comme Lama sans connaitre Lama.
Le serveur reste la source de verite : etat, actions autorisees, raccourcis,
tour courant et erreurs. Le client affiche une interface clavier generique et
renvoie les actions exposees.


Ce qui est implemente cote client-wx
------------------------------------
Module cree :

- `client-wx/src/modules/gameplay/domain`
- `client-wx/src/modules/gameplay/application`
- `client-wx/src/modules/gameplay/infrastructure`
- `client-wx/src/modules/gameplay/presentation`

Responsabilites :

- `domain` : modeles neutres (`GameState`, `GameAction`, `GameShortcut`,
  `GameLine`, `GameEvent`).
- `infrastructure` : WebSocket `/ws/game`, ticket scope `game`, codec JSON
  tolerant.
- `application` : `GameSessionService`, boucle de reception temps reel.
- `presentation` : `GamePlayPanel`, interface wx clavier-only.

Decoupage presentation :

- `GamePlayPanel.cpp` : cycle de vie du panneau uniquement.
- `GamePlayPanel.Layout.cpp` : construction wx.
- `GamePlayPanel.Session.cpp` : appels asynchrones et session gameplay.
- `GamePlayPanel.Events.cpp` : clavier, Enter, F5 et raccourcis serveur.
- `GamePlayPanel.State.cpp` : application de l'etat serveur et rendu texte.
- `GamePlayFormatters.*` : formatage JSON generique.

Integration :

- `GameComposition` cree `GameSessionGateway` et `GameSessionService`.
- `AppNavigator` injecte le service gameplay dans `RoomPanel`.
- `RoomPanel` affiche `GamePlayPanel` quand la table est demarree.
- Avant demarrage, l'ancre de table existante reste utilisee pour les actions de
  room.


Temps reel backend supporte
---------------------------
Le client wx utilise maintenant :

- endpoint : `/ws/game`
- ticket WS : scope `game`
- messages envoyes :
  - `game.join`
  - `game.state`
  - `game.actions`
- messages recus :
  - `game.state`
  - `game.ack`
  - `game.turn`
  - `error`

Le client ne modifie jamais l'etat localement apres une action. Il attend le
nouvel etat serveur.


Interface clavier-only
----------------------
Pas de boutons d'action visibles.

L'ecran gameplay est compose de :

- un en-tete compact ;
- une liste verticale focusable d'actions/lignes de jeu ;
- un panneau d'information ;
- un journal ;
- une ligne texte avec les raccourcis disponibles.

Comportement :

- fleches haut/bas : naviguer dans la liste ;
- Enter : executer l'action de la ligne selectionnee ;
- F5 : demander un nouvel etat ;
- raccourcis serveur :
  - `type: interface` : change le panneau local (`score`, `hands`, `discard`) ;
  - `type: action` : cherche une action exposee du meme type et envoie
    `game.actions`.

Les panneaux d'interface sont lus en priorite depuis `extras.ui.panels[id]`.
Si un panneau fournit `title` et `message`, le client affiche ces deux champs.
Sinon il affiche le JSON de maniere generique.

Important :
Le client ne calcule pas si une carte est jouable. Il execute seulement l'action
deja exposee par le serveur.


Contrat serveur consomme
------------------------
Le codec lit :

- `roomId`
- `gameType`
- `version`
- `status`
- `phase`
- `turnLabel`
- `actions`
- `log`
- `metadata`
- `extras`
- `extras.ui.panels`
- `extras.shortcuts`

Format des raccourcis supporte :

- `pressed SPACE`
- `pressed S`
- `pressed E`
- `pressed C`
- `pressed P`
- `pressed Q`
- `pressed ENTER`

Le parser normalise :

- `pressed SPACE` -> `SPACE`
- `pressed RETURN` -> `ENTER`
- `pressed BACKSPACE` -> `BACK`


Principe anti-dette
-------------------
Interdit dans `client-wx` :

- condition specifique a Lama ;
- regle de jeu locale ;
- calcul local des cartes autorisees ;
- suppression locale d'une carte jouee ;
- affichage par jeu.

Controle actuel :

- aucune reference specifique a `lama` n'a ete ajoutee dans le module gameplay ;
- la seule comparaison de `gameType` sert a savoir si la session deja ouverte
  correspond a la table courante.


Limites restantes a verifier sur Windows
----------------------------------------
L'environnement Linux actuel n'a pas `cmake`, donc la compilation locale n'a pas
pu etre lancee ici. A verifier sur Windows :

1. generation CMake ;
2. build `lemonde_de_lila_wx` ;
3. connexion `/ws/game` avec ticket `game` ;
4. ouverture d'une table Lama ;
5. reception du premier `game.state` ;
6. affichage des actions en liste verticale ;
7. Enter sur une ligne ;
8. raccourcis `SPACE`, `S`, `E`, `C`, `P`, `Q`.


Point backend a clarifier
-------------------------
La documentation backend dit que les clients peuvent envoyer les touches via
`game.key`, mais le handler actuel traite specialement surtout `ENTER` et `X`.

Pour eviter d'attendre une correction backend, client-wx utilise pour l'instant
la strategie suivante :

- shortcut interface : local uniquement ;
- shortcut action : conversion vers l'action exposee, puis envoi via
  `game.actions`.

Cette strategie respecte le contrat serveur parce que seules les actions deja
exposees au joueur sont envoyees.


Definition de fini pour Lama
----------------------------
Lama sera considere jouable dans client-wx quand, sur Windows :

- une table Lama peut etre demarree ;
- le panneau gameplay remplace l'ancre de table ;
- `game.join` retourne un `game.state` ;
- les actions apparaissent verticalement ;
- Enter execute l'action selectionnee ;
- Espace pioche seulement si le serveur expose le shortcut `SPACE -> draw` ;
- S affiche score ;
- E affiche mains ;
- C affiche defausse ;
- P execute l'action exposee par le serveur ;
- Q execute l'action exposee par le serveur ;
- aucun code specifique a Lama n'est ajoute.
